## 160 — 2026-09-05 — previz 脚本改名：认 `shot{NN}_previz.py`

> target_stage: 6
> target_artifacts:
>   - libs/infrastructure/writers/previz__writer.py
> severity: low

### 起因

`ai_video.md` 新增 rule 4h §C：per-shot 的 S 档 previz 编排脚本必须叫 `shot{NN}_previz.py`，
**不得与仓库通用引擎 `tools/previz/build_previz.py` 同名**——同名会让一份合法的 per-shot
脚本在盘上看起来像「引擎被 fork 了一份私货」，也让真正的 fork 无法被一眼认出。
xianjian_yi_mv 的 `shots/shot12/previz/build_previz.py` 据此更名为 `shot12_previz.py`。

### 改了什么

`PrevizWriter._rebuild()` 原本按硬编码文件名 `build_previz.py` 找脚本、并从中解析
`SCENE_MASTER` 常量来重建 blend。抽出 `_build_script(previz_dir)`：
`shot*_previz.py`（glob，取排序首个）优先，`build_previz.py` 作旧名兜底，都没有则返回
`None`、维持「按现状渲染 blend」的旧行为。

### 教训

**改文件名要连工具链一起改。** 这个 writer 是按文件名找脚本的，只认旧名的话，
改名当天 webapp 的「出片」按钮就会**悄悄不再重建 blend**——不报错，只是渲的是上一版几何。
这类「静默降级」比报错危险，因为没人会去看。已把这条写进 `ai_video.md` rule 4h §C。

### 需求

在 `ai_video_management` webapp 里新开一个**调研（research）模块**，承载一份
「近半年 YouTube AIGC 视频系列选题排行」调研结果：**10 大系列**，每个系列下
**10 条 example 视频链接**。

### 两条硬筛选标准（用户口述，优先级最高）

1. **回报/收入好** —— 判据是 **点赞率（like/view）高 + 播放量（view）高**。
   两者都要看，不能只看其一：高播放低赞＝标题党/推荐流意外；高赞低播＝小众。
2. **一个人能翻拍（solo-replicable）** —— 用户是**单人作业**：
   - **工具不是约束**：现有链路是 Claude + Cascadeur + Blender + ElevenLabs + Seedance，
     但缺什么工具「可以很轻松买」，所以不要因为「需要某个付费工具」而淘汰一个系列。
   - **人力是硬约束**：凡是需要真人出镜/实拍/摄制组/配音演员/专业剪辑团队，
     或单集需要数十小时手工建模动画的系列，**直接淘汰**。
   - 判据措辞应写成「单人 + 可购买工具，多少小时/集」，而不是「是否只用现有 5 个工具」。

### 系列（series）的定义

「系列」＝**可复制的内容格式/品类**，不是某一个频道，例如：荒野求生、AI 武侠剧、AI 跳舞。
一个系列下的 10 条 example 必须是真实存在、可打开的 YouTube 链接。

### 数据必须真实、可验证

播放量/点赞数/发布日期一律取自 `yt-dlp` 实测，不得凭印象或搜索摘要估算；
调研窗口 = 近半年（2026-03-06 起）。

### 交付形态

- 数据落盘为结构化文件（可被 webapp 读取、可复跑刷新）。
- webapp 侧新增一个「调研」模块（导航入口 + 页面），可按点赞率/播放量/翻拍难度排序浏览。

## 162 — 2026-09-06 — 调研模块要做成「可管理的工作台」，不是 JSON 阅读器

> target_stage: 6
> target_artifacts:
>   - apps/ui/src/components/Research*.tsx
>   - libs/infrastructure/writers/research__writer.py
>   - apps/api/app_factory.py
> severity: medium

### 用户原话（要点）

「don't just give me a json file to read on UI，我要 UI 的原因是你可以给我建一个
feature rich、multilayer 的 UI 来 **view + manage** 内容。」

### 抽象出的规则（对所有数据型模块通用）

1. **把数据落成 JSON 再渲染一张表 ≠ 交付了一个 UI 模块。** 用户要 webapp，是要
   **多层次、可操作**的界面：能概览、能钻取、能筛选、能对比、能留下自己的判断。
   只做「只读渲染」等于把 JSON 换了个字体。
2. **「manage」＝ 用户的决定要能被持久化**，并且**与被管理的数据分文件存放**——
   数据可以随时重新生成，用户的决定不能被生成过程覆盖。
   本模块的落法：`{dataset}.workspace.json` 与 `{dataset}.json` 并排放，前者按
   slug / video_id 引用后者，所以重跑调研后状态/评分/笔记依然对得上。
   （与 `promoted.md` 在 regen 中被 preserve 是同一条原则。）
   推论：数据集列表必须排除 `*.workspace.json`，否则用户的决定会被当成一个数据集列出来。
3. **深链接是功能的一部分，不是可选项。** 一旦视图状态（tab、打开的条目）进了 URL，
   直接打开或刷新就必须能还原；SPA 回落缺失会让「多层次 UI」在刷新那一刻全废。
   `StaticFiles(html=True)` 只对目录路径回落，必须补 catch-all，
   但 `/api/*` 要保持 JSON 404，不能返回 HTML 外壳（否则客户端极难排错）。

### 交付形态

调研模块从「一页卡片列表」改为四视图工作台 + 详情抽屉：
总览（象限散点）/ 系列（筛选+定状态+评分）/ 样本库（100 条可查询表）/ 对比（并排矩阵）。
