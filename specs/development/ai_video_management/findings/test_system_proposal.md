### 1.2 由此推出的工程原则

1. **只有确定性检查可以阻断。** 阻断点只有五处：代码改动收尾时的 T0（含「改动必带测试」与测试条数棘轮）；现有编译门禁；现有资料包门禁；提交前的重试计数；改数据格式时的迁移门禁。读活数据的检查不进阻断层（登记表的 `reads_live` 字段，由 `testlab check` 强制）。
2. **LLM 结论只作参考。** 它附在批准请求上，最多 5 条稳定的 blocker / major，加上「作者意图没落地」的条目；你照样可以确定。你对每条的处理（采纳 / 不采纳 / 误报）都记下来，用来算精度、决定检查器去留。你书面授权代理自主确定时（例如 shengji follow-up 031），报告附进那次授权的记录，按授权条款处理。
3. **纳入范围零抖动。**
   - 确定性测试不读活数据、不联网，不依赖时钟和执行顺序。跑哪些套件由登记表静态决定，不按当次机器的快慢截断。
   - 夹具和金标先做换行归一化，再算 sha 或比对；换一种方式 checkout，结论不变。
   - 抖动的测试当天隔离，7 天内修好或删除。到期只在摘要里提示，不改变 T0 是否通过。
   - LLM 部分套一层「确定外壳」：输入包 sha 固定，输出结构固定，计分由代码做，原始输出落盘、可以重放。同样的原始输出，永远得出同样的报告和分数。采样本身的波动用「3 次里至少 2 次」吸收，并标出支持度，不进阻断层。
4. **棘轮。** 修 bug 先写失败测试；每次运行记下各套件的测试条数，条数下降而没有退役记录就判红；基线只在明确接受时更新并写明原因；用例只退役、不删除。
5. **隔离审稿在 harness 之外。** 由脚本直接起 `claude -p`。工作目录放在系统临时目录、任何仓库之外，审稿人只拿到观众看得到的材料。事后回放，核对它加载了什么、读了什么。凡是经工作流子代理跑的「盲审」，一律不计分。
6. **一个名字一处定义。** 问题类别、状态词、重试计数、回执分流、资料包状态、内容指纹，各只有一份实现，别处都调用它。暂时做不到的，用差分测试锁住两边结论一致。
7. **先证明再加。** SKILL.md 第 27 行写着：「新规则先明确解决什么问题，再比较是否改善，不自动增加审查层。」所以冷读默认关闭，有了数据、经你同意，才默认附上。

### 3.2 各层定义

| 层 | 在本仓库指什么 | 例子 | 断言方式 | 档 · 批次 |
|---|---|---|---|---|
| unit | 一个纯函数、一条规则 | 回执分流；重试计数；状态行解析；`upload_tags` 给同类文件各自编号；探针阈值；冷读结果的聚簇与计分 | 阻断 | T0 · 1a |
| component | 一个工具或类，在临时目录里整体跑 | `shot_pack sync` 的建 / 更新 / 失效；`shot_take submit/poll/record` 接上替身；读取器遇到坏文件时降级 | 阻断 | T0 · 1a-2 |
| contract | 两方共用的格式或规则 | 资料包状态、回执分流、内容指纹、`COMPILER_VERSION` 各只有一份实现；overhead 的每个键都有读取者；`prompt.txt` 与 `prompts.json` 逐字一致 | 阻断 | T0 · 1a |
| integration | 跨代码库的文件交接，不联网 | 应用编译 → 工具建资料包 → 提交命令；条目录 → renders 读取器 → API | 阻断 | T0 · 1a-2 |
| system | 一部迷你剧走完整条生产链（不开浏览器、不真出片） | 见 §0 的表 | 阻断 | T0 · 1a-2 最小版 |
| end-to-end | 管道（系统测试 + 浏览器，用夹具）、创作（冻结故事 → 代理写分镜 → 编译 + 冷读）、媒体（一次真实出片） | 见 §0 的表 | 管道阻断；创作只作参考；媒体只作信息 | 第一阶段只有 system 最小版；管道、创作在二；媒体只由你点 |
| regression | 已发生的问题不再出现 | 代码类：B-001～003 先写失败测试。内容类：用例库 L01–L07 | 代码类阻断；内容类用来检验检查器，计入评测 | T0 · 1a；用例库在 1a-1 |
| 内容评测（冷读） | 独立审稿人读故事 / 分镜，不看成片 | 冷读 + 意图落地 | 只作参考 | T1 · 1b |
| 成片评测 | 看成片 | 技术探针（确定性）；整场冷看、逐拍核对（看图） | 探针只提示；看图只作参考 | T0 · 1a-2；T2 · 二 |
| 基准 | 冻结夹具 + 指标 + 基线 + 改前改后比较 | 编译金标（逐字）；冷读基准；指南重写基准 | 金标阻断；LLM 基准只给数字 | T0 · 1a-1；T1 · 1b；二 |

目标形状：unit 与 component 占条数的八成以上；contract、integration、system 加起来几十条；浏览器 E2E 个位数；LLM 只在批准前、改检查器或你要的时候跑。

## 5. 目录、登记表与格式

### 5.1 唯一的新根目录：`testlab/`

理由：
- 仓库里已有多个 `tests/`（应用、tools、assets）。再建一个根 `tests/` 容易混淆，pytest 也容易误收；`testlab` 一眼就能认出来。
- 它放的是**测试数据**：类别、用例、夹具、金标、基线、登记表。它们不是给代理读的规则，所以不放 `.agents/references/`。
- 现有测试原地不动。检查器 prompt 属于流程本身，放在流水线 skill 里。不再另建 `qa/`、`tests/`、`tools/accept/` 这类第二个根目录。
- `tools/` 是没有 `__init__.py` 的命名空间包，同一目录下同名的 `testlab.py` 和 `testlab/` 会互相遮蔽，所以实现代码放进 `tools/testlab_lib/`。

### 5.5 付费服务替身

- **接缝。** `tools/service_call.py` 读环境变量 `MDP_FAKE_DREAMINA`（值是场景脚本的路径），有这个变量就把执行器换成替身；`RequestLog.cli` 加一个可选的 `runner` 参数，默认仍是 `subprocess.run`。不设变量时，生产行为完全不变。请求日志照常写，所以「先写日志再调用」这一条本身也在被测范围内。
- **数据根接缝。** 工具里的 `REPO` 现在既是代码根又是数据根：`shot_take` 有 5 处、`shot_pack` 有 3 处 `relative_to(REPO)`，参考按 `REPO / ref["path"]` 解析，`service_call` 以 `cwd=REPO` 启动。把它拆成代码根和数据根（`MDP_DATA_ROOT`）；不设时行为不变。
- **替身不得写进真实日志。** 请求日志的位置由 `--target` 推出；数据根一旦指错，假的「受理」回执就会追加进真实的 `ai_videos/…/request_log.md`，污染 UI 上的「请求日志」和重试计数。所以：替身模式下，解析出的日志路径只要落在仓库的 `ai_videos/` 内，就以非零码退出；每条假事件写 `"fake": true`，计数器和 UI 一律跳过；另用一条测试证明假调用写不进仓库。
- **回放。** 按场景脚本的顺序回放；多个 `service_call` 子进程之间靠游标文件接续，游标放在每个测试自己的临时目录里，用 `os.replace` 原子更新。收到脚本以外的调用，就以退出码 97 报「UNEXPECTED CALL」——多提交一次、多扣一次费，测试直接失败。
- **回执样本。** 从全部 `request_log.md`（5 份，179 条 Dreamina 结果）里抽取并脱敏：prompt 只留首行，URL 去掉签名，submit_id 换成固定假值。第一阶段只收场景要用的：受理、排队、成功 3 种正常形态，加日志里出现过的 6 种失败形态（提交时上传阶段失败、提交时 apply 阶段失败、final generation failed、视频下载 TLS 超时、图片下载 TLS 超时、查询超时且输出为空）。
- **绊线**（`testlab/tests/conftest.py`，autouse）：socket 只许连 127.0.0.1；`HOME`、`USERPROFILE` 指向临时目录；子进程的 PATH 用白名单，只留解释器和 ffmpeg 所在目录；`dreamina`、`codex`、`claude` 各有一条测试证明调不到；写入守卫用 `sys.addaudithook` 拦截以写模式打开仓库路径的操作，只放行 basetemp 和 `.audit`。

## 6. 运行入口与触发时机

**一个入口**：`python tools/testlab.py`。它只用标准库，每个套件都用登记表里声明的解释器启动（`<venv>/Scripts/python.exe -m pytest …`）。缺了前提（解释器、claude CLI、ffmpeg、媒体文件），就标「未跑」，绝不标「通过」。

## 8. 检查器自己的测试

### 8.1 确定性检查

- **先红后绿。** 每条新的确定性测试，都要亲眼看到它失败一次：bug 类在修复前的代码上失败；守卫类在故意破坏的临时副本上失败（例如去掉宽高比补边）。Validation 里写明「先红：<测试名> 在 <修复前 / 临时破坏> 上失败」。不建变异测试框架。
- **零抖动规则。** 不 sleep，用 `os.utime` 直接改时间；不联网（靠绊线保证）；不读活数据（`reads_live` 的套件只报告）；`shot_take` 在测试进程里跑，`time.sleep`、下载退避、`datetime.now` 都打桩；每条测试用自己的临时目录；写入守卫拦截一切写到 basetemp 和 `.audit` 以外仓库路径的操作。不用「跑前跑后 git status 不变」来验收，因为别的会话随时在改仓库。
- **换行。** 本机 `core.autocrlf=true`，仓库没有 `.gitattributes`，冻结包现在就是 CRLF（`story_cold_open.md` 里 20 个 CR 对 20 个 LF）。所以提交任何夹具、金标之前先加 `.gitattributes`；夹具 sha、金标比对、prompt 逐字比对，一律在换行归一化之后做；再加一条测试：CRLF 副本必须得出同样的摘要和结论。
- **解释器。** 每个套件用登记的解释器。tools 和 testlab 自身的测试用根 `.venv`（3.11，与生产里的系统 Python 同版本）。迷你剧系统测试里，应用一侧在项目 venv 里跑，工具一侧照生产方式用 3.11 起子进程。
- **Windows 约定。** 设 `PYTHONUTF8=1`、`PYTHONDONTWRITEBYTECODE=1`；pytest 的 `--basetemp` 用短路径，由运行器强制，路径过长就拒绝运行（实测：basetemp 在深路径下，`test_compile_import_and_navigation_share_the_same_key` 以 WinError 206 失败；默认路径下 35/35 通过）；PIL 一律用 `with`，删文件前先关句柄；第二阶段的浏览器 E2E 用独立端口 8799，按 PID 启停，绝不按进程名杀。
- **验收。** `t0` 连跑 3 次，逐条结果一致；写入守卫的自测证明它真的会拦。
- **抖动处理。** 发现时好时坏的测试，当天把状态改为 `quarantined`，写明原因、负责人和期限（≤7 天），到期前修好或删除。不加自动重试。
- **探针自测。** 用 ffmpeg lavfi 现做 6 种坏样本（截短、错误分辨率、去掉音轨、加 20 dB、同场拼接、冻结），每种都必须报出来。阈值写成常量并配单测：
  - 时长比请求短 0.15 s 以上，判截短；
  - 帧率按 `avg_frame_rate`（或帧数 ÷ 视频流时长）算，不在 23.5–25 之间就报。ep01 19 条真实条的 `r_frame_rate` 都是 60/1，`avg_frame_rate` 才是 24.07–24.15，用错字段会全部误报，所以另加一条测试：r_frame_rate 为 60/1 的真实条不报；
  - scene ≥0.15 判内切（自然条最大 0.050，人为拼接 0.324）；冻结 ≥1 s 或黑场 ≥0.2 s 就报（人为造的 1.5 s 冻结在 2.47 s 处被检出）；真峰值 > −1 dBTP 给提示。

  ep01 19 条真实条 0 误报，作为一次性验收记在 follow-up 里，不进 T0：mp4 只在本机，属于活数据。

### 8.2 冷读怎样做成可重复、可度量

1. **隔离运行。** 由 `tools/testlab_lib/isolate.py` 直接起子进程，不经工作流 harness。
   - **预检（确定性）。** 工作目录一律新建在系统临时目录。从工作目录逐级查到盘根，不得有 `CLAUDE.md`、`AGENTS.md`；`.claude` 只允许是用户主目录下的用户级配置（另记指纹）；在工作目录里 `git rev-parse` 必须失败。环境变量用白名单，只留登录与系统必需的几项。`apiKeySource` 必须是 none（用订阅额度）：环境里带了 key，就成了按量计费的服务，要先走请求日志，所以拒绝运行。
   - **参数：**
     ```
     claude -p --safe-mode --restricted --strict-mcp-config --disable-slash-commands \
       --no-session-persistence --tools "" --model claude-opus-5-5 --effort high \
       --system-prompt "<模板生成的系统提示>" --json-schema "<schema>" \
       --output-format stream-json --verbose --max-budget-usd 1 < packet.md
     ```
     `--system-prompt` 替换默认系统提示，默认提示里的工作目录、环境和 git 状态几段随之去掉，CLI 升级也不会悄悄改掉提示。文字层的审稿人一个工具都没有；看图版（第二阶段）改用 `--tools Read`，临时目录里只放联系表和字幕。这些参数都在本机 claude 2.1.296 的帮助里核实过存在；能否同时使用，第 0 步实测，不兼容就由外壳做 schema 校验，不合格时重问 1 次。
   - **资源。** 并发不超过 3；单次超时 10 分钟，超时只按自己的 PID 收尾（`taskkill /PID <pid> /T`）；被限速或失败的运行标「未审」，不靠缩小 N 凑数。
2. **观众投影。** 按字段、按小节的白名单取材料。故事只给该小节正文（段落编号 P1、P2…）和此前的小节；分镜只给看得见、听得见的字段（画面、走位、动作、镜头、光线、台词），去掉 purpose 和决策记录，以前一场作上下文。投影由适配器按格式版本生成（`project.py`），配投影金标测试。意图落地要读的「目的 / 结束时的变化 / 同情来源」，第 0 步从 s2 决策记录里摘出，冻结进 `fx-ep01-s2-intent@v1` 并过泄漏扫描：这些记录在你报告之后改写过，已原样引用你的原话（`decisions/story.md:126–128`、`scenes/s2/decisions.md:52`、`decisions/filming.md:78–80`），又没进 git，报告前的版本无法还原。摘录过不了扫描，就不跑意图落地，K14 保持 experimental。
3. **回放核对。** 解析 stream-json 的初始事件：工作目录等于本次临时目录；工具、MCP 为空；plugins 只许清单内的内置插件（D3 的干净试点里，初始事件仍显示加载了内置插件 `cc-plugin-agents-md`、19 个 skills 和 5 个 agents）；skills、agents 为空；型号与固定值一致；`apiKeySource` 为 none。文字层不得有任何工具调用。任何越界，这次运行都标「未审」：不计分、不显示、作废重跑。
4. **隔离金丝雀。** 每次 CLI 或模型换版跑一次：在工作目录和上一级同时放写有随机暗号的 `CLAUDE.md` 与 `AGENTS.md`，并核对用户级配置指纹（`~/.claude/settings.json` 的 hooks、`~/.claude/skills`、已装插件）；输出里不得出现暗号。
5. **泄漏与过拟合扫描。** 输入包必须等于已确定版本的确定性投影（sha 一致）；「答案文本」（你的原话、用例的 `reads_as` / `expect`）里只要有源文中不存在的片段出现在输入里，这次运行就不计分（中文连续 8 字，拉丁文连续 5 词）。第 0 步的冻结包已经扫过：与 5 个缺陷描述的 8 字重合为 0。prompt 侧见 §5.6。生产运行命中扫描，同样标「未审」、不显示。
6. **采样与合并。** 每个单元并行采样 N=3。发现按（层、位置、类别）排序，把「类别同族、位置相差不超过 1」的连成图，每个连通分量算一簇；这样分簇与处理顺序无关，replay 才能逐字一致。支持度记为 k/3。显示规则：≥2/3 的 blocker / major 排在最前；批准请求只放前 5 条，按（严重度、支持度、位置、类别号）排序；稳定的 minor 和只出现 1 次的「偶发」默认折叠；每个单元最多 8 条。
7. **意图落地。** 另起一次调用，不污染冷读本身。输入是场的 purpose、冻结的意图摘录、冷读的复述；对 3 份复述各跑一次，≥2/3 判「没落地」才报。
8. **计分（只在基准里用）。** 由代码判，不用 LLM 判官。一条发现要同时满足三条，才是某个（用例, 层）的候选配对：类别属于「用例类别 ∪ also ∪ 同族」；位置与锚点相差不超过 1；严重度不低于 `severity_min` 减一级。然后做**一对一指派**：每条发现最多记给一个用例，优先级依次是精确类别 > also > 同族、距离近的优先，平局按（用例号、发现位置）的固定次序打破。一次采样里被指派到就算「抓到」；3 次里 ≥2 次抓到，才算「稳定抓到」。
9. **版本记录。** 每次运行写 manifest：模板、类别表、schema、拼好的 prompt 和每个输入文件的 sha256；固定型号与初始事件报告的型号；CLI 版本、effort、用户级配置指纹；耗时与 `total_cost_usd`。任何一项变了，就是检查器的新版本。
10. **漂移复测。** 换模型或 CLI 大版本时，重跑基准、立新基线（不算退化）；第二阶段再加每周重放。

**这些门槛的误判率**（按二项分布粗算）：
- 检查器单次检出率为 0.8 时：单个用例被判「稳定抓到」的概率约 0.90；故事层判 go 的概率约 0.97，分镜层约 0.94。
- 单次检出率只有 0.4 时：故事层仍判 go 的概率约 0.28，分镜层约 0.13。

参照：早先盲审里，额外发现的「成立」比例约为 0.56–0.65。这个数字来自被污染的运行，只作参照。所以精度 ≥0.7 在第一阶段未必能达到；达不到就保持手动，不降低门槛。

## 9. 测试库如何成为每次工作流改进的一部分

### 9.1 你报的每个问题 → 用例

1. follow-up 记下你的原话。
2. 代理把它归进现有类别；归不进的标「待定」，同类问题在 ≥2 个不同场景出现，才建新类别。
3. 代理起草用例（观众语言 + 锚点 + 各层期望）；你确认类别和严重度之后，转为 active。代理或审稿人自己发现的，只能是 candidate。
4. 用当前的检查器跑这个用例，按结果分三种情况：
   - 抓到了，只是流程里没跑 → 修触发点；
   - 抓不到 → 按类别改检查器（走改动单），不写特判；
   - 是代码或数据的 bug → 先写失败测试，再修。
5. changelog 写明新增了哪些用例、指标怎样变化；用例的 `source` 字段指向这个 follow-up。

### 9.2 改动分级与执行点

| 改什么 | 同一次改动里必须带 | 怎样算变好 | 缺了怎样 |
|---|---|---|---|
| 工具、应用代码 | 登记套件里有新增或修改的测试；新 bug 先有失败测试 | T0 全绿 | 收尾档判红 |
| 编译器 | 同上，加 s2 编译金标的更新 | 每处 diff 都有解释；版本号已升；资料包失效的数量与预期一致 | 收尾档判红 |
| 数据格式 | 升格式号 + 迁移锚点 | `coverage --strict` 退出 0 | 收尾档判红 |
| 检查器（`playbooks/`、`testlab/categories.toml`；1b 起） | 改动单 + 冷读基准（N=3，同一夹具，先测噪声底） | 满足 §8.4 的合入条件；由你决定 | 收尾档判红 |
| 创作指南（`.agents/skills/ai-videos-pipeline/` 下的其余文件） | 第一阶段：改动单写明目标类别与目标用例，标「观察中」，在真实使用中看冷读和你的看片结果。第二阶段：重写基准 | 第二阶段：目标类别在两臂中方向一致地下降，其他类别和检查违例不退 | 只提示 |

执行点是 `testlab check --changed`：`tools/`、`projects/ai_video_management/`、`.agents/skills/ai-videos-pipeline/**` 有改动时，同一次改动里必须有下列之一——登记表里的测试有新增或修改；有 `source` 指向本 follow-up 的用例；有 `touches` 列出该文件的改动单；有写明原因的 `kind = "no-test"` 单（例如纯文案、删死代码）。快速档只提示，收尾档正式执行。

纪律：尺子和被量的东西，不在同一张单里改。改指南时，检查器版本冻结；改检查器时，用例库冻结。改动单样例：

```toml
# testlab/changes/CH-20261014-01.toml
id = "CH-20261014-01"
kind = "checker"                  # checker | guide | no-test
title = "冷读：先逐拍复述，再找问题"
touches = [".agents/skills/ai-videos-pipeline/playbooks/cold-read.md"]
target_cases = ["L01"]
frozen = ["testlab/cases", "testlab/categories.toml"]
red_first = "改前那一版：L01 在分镜层 0/3（确认是红的）"
bench = "cold_read --n 3"
status = "proposed"               # proposed → measured → accepted | rejected | parked | observing | reverted
follow_up = "development/ai_video_management#NNN"
```

### 9.3 棘轮与基线

- **测试条数只增不减。** 每次运行都记下各套件收集到的条数。条数低于 `baselines/counts.json` 里的下限，又没有 `retired.toml` 的退役记录，也没有删除被保护的源文件，就判红。确定性测试只能随它所测的代码，在同一次改动里删除。
- **基线。** `baselines/*.json` 只在执行 `bench … --accept --why "<原因>"` 时更新。复现靠文件的 sha256，不依赖 commit。
- **回退只作为提议交给你。** 改动单落地前，先保存每个被改文件的快照和 sha；之后重跑时召回下跌超过 0.2，或你又报出同类问题，就把回退方案交给你；执行前核对文件当前 sha 仍等于改后的 sha，不覆盖别人后来的改动。不按 git 还原：多数新流程文件不在 git 里，对已跟踪的文件做 `git checkout` 还会抹掉其他会话未提交的改动。

### 9.4 格式迁移时用例不丢（迁移门禁）

- `formats.toml` 记录每一层的格式号和格式指纹。指纹只算锚点解析和观众投影**实际读取**的字段白名单：
  - 先把现在写在校验语句里的字段集抽成常量（`episode_workflow__reader.py:41`、`:47`；entity 的 `:28`、`:33`、`:40`、`:181`、`:188`）；
  - 这些字段变了却没升格式号 → 红；
  - 与投影无关的字段增删不触发。所以 RCA 要加的「画面方向」「每人每拍的动作与视线」不会让门禁频繁变红，除非投影要读它们。
- `coverage --strict`：每个 active 用例、每个 required 的层，都必须有当前格式的锚点，并且有一个登记过的检查器（manual、experimental 或 active）声明覆盖这一层和这个类别；缺了就退出 1。should 层只报告，等对应的检查器转为 active 后再纳入；deferred 层不查。它只看结构，所以是确定的，可以阻断。
- 背景：旧闸门有 7 条单测一直全绿，却只认旧格式「0–8s」，换成新格式「秒」之后，实测解析出 0 拍。§2.2 的死键也是同一种「静默失效」。

### 9.5 指标（只看趋势）

每出完一批片，按场记一行：逃逸率、发现层分布、每个保留镜头的积分、每镜条数、搁置率。冷读另记回溯召回（你后来报出的设计问题里，批准时报告已有稳定发现的比例）和实用精度（你采纳的比例）。第一阶段随 follow-up 摘要手工记，第二阶段由 `testlab metrics` 计算。基线见 §7 末尾。

### 9.6 Validation 贴测试摘要

每个 follow-up 的 Validation 都贴 §6 的那行摘要，其中含「新增测试 n · 用例 n · 改动单 n」。修缺陷时写上用例编号；改检查器或指南时，写上改动单编号和前后指标。

### 9.7 退役与治理

| 问题 | 规则 |
|---|---|
| 谁加用例 | 你报的：代理起草、你确认。代理发现的：只能是 candidate |
| 谁改检查器 | 谁都可以，但要走改动单，而且不能同时改它的用例 |
| 什么可以阻断 | 只有 §1.2 第 1 条列出的五处 |
| 抖动的测试 | 当天隔离，7 天内修好或删除；到期只在摘要里提示，不影响 T0 的结论 |
| 删除过时的测试 | 删代码或格式时，在同一次改动里删掉对应的测试，并写退役记录。用例永不删除，只 retire 并写明原因。检查器要退役，前提是别的检查器对它全部用例的召回都不低于它 |
| 季度清单 | 每季度列出「90 天没失败过、所保护的源也没变」的套件，由人决定去留 |

## 10. 搁置机制

### 10.1 3 轮怎么计

计数只有一份实现，放在两边都能导入的 `libs/common/`，提交工具、搁置清单和以后的 UI 共用。轮数从请求日志算，请求日志是唯一来源。

- **一轮** = 回执分流（唯一实现）判为「已受理」的一次提交。上传阶段（含 ApplyImageUpload）的失败不算，不论回执带不带 ID。下载失败只重下、不重提，也不算。
- **受理后服务端生成失败，算一轮。** 回执里看不出是否退费，按受理来算最保守。shengji 031 授权里写的「服务端或网络失败（上传 / 下载阶段、未扣费）不计轮次」，与此一致。
- **按「镜头 × 设计版本」累计。** 设计版本 = 这一镜在已确定分镜里的内容指纹（唯一实现），提交时写进 `generation.json`；旧条没有这一项的，按同一个设计计。原样重出、换参考、补资产、编译规则改动，都算同一个设计。分镜改了这一镜，并经过确定之后（你确定，或者在你书面授权的 follow-up 范围内由代理确定），从 0 开始计。
- **谁确定的、依据什么。** 第一阶段由代理写进决策记录：你的原话，或者授权 follow-up 的编号。这可以审计，但 UI 只读，系统无法强制校验。结构化的确定记录（RCA R7）要改三个模块文件的格式，放第二阶段。
- 同一原因连续两轮（例如两次服务端失败、两次视线不对），第三轮之前必须换方案，并写明换了什么。
- 历史轮数从请求日志复算，不补建历史条目录（AGENTS：不补造历史请求）。实测：用 ep01 的请求日志复算，st5 = 3 轮（两次服务端失败之后成功）；s1 st1 的 9 次上传失败不计。

### 10.2 提交前检查（确定性，阻断）

```
✗ ep1_s2_st7：同一设计已用 3/3 轮，建议搁置。
  清单：python tools/testlab.py parked ai_videos/shengji_zhilu/episodes/ep01
  继续需要依据：python tools/shot_take.py submit … --over-budget "<你的原话>"
             或 --over-budget "follow-up <编号>"（该授权须写明覆盖这一镜的轮次上限）
```

依据写进请求日志。CONVENTIONS「Iteration bounds」允许你用书面授权覆盖默认轮次，例如 follow-up 231 的夜间授权；没有这种授权就停。shengji 031 自己写的也是「每镜同一设计最多 3 轮」，所以它不放行同一设计的第 4 轮。

### 10.3 搁置单写什么

搁置时，代理停下这一镜的工作，在下一条消息和 follow-up 摘要里附上搁置单。搁置单写在该镜最新一条 review.md 里：状态行写「状态：搁置」，再加一节「## 搁置讨论」，包括：

1. 涉及哪些镜头，是否跨镜同因；
2. 每一轮的表现，按出片执行偏差的类型标记：人数或分身、身份漂移、道具走样、机位景别、动作不符、方向翻转、伪影、声音违规、状态没画出；
3. 已经试过的改法；
4. 判断：设计层 / 执行层 / 参考资产 / 能力上限（规则见 §10.5）；
5. 可选方案，各附积分估算；
6. 需要你决定什么。

样例（按出片设计试点的真实情况整理）：

> **s2 · 衬衣上的泥（跨镜同因）**
> - 涉及：st7、st10、st11、st12。逐拍核对 8/8 次判「部分」或「否」；整场冷看 3/4 次报「衬衫太干净」。
> - 已经试过：分镜写了「衬衣左半边…糊满湿泥」，st12 提交时已带上。
> - 判断：执行层，跨镜同因（Seedance 对「脏」的描述响应弱，作者审核早有记录），所以不逐镜重出。
> - 选项：① 出一张「一身泥」状态的三视图作参考（图片可由代理出，先记日志），只重出 st10，约 120 积分；② 改分镜，泥只落在裤腿和手上；③ 接受，剪辑时不强调衬衣。

### 10.4 适用范围与给你的选项

「≤3 轮 → 搁置 → 共同讨论」同样适用于：资产出图（同一资产、同一张卡）；检查器改动单（3 版都不过）；第 0 步的冷读模板（含首版共 3 版）。

给你的选项：改设计（回到故事或分镜，确定后计数清零）；换镜头（拆镜、换景别、加反应近景）；补资产（例如状态参考图）；剪辑绕过；接受瑕疵。讨论结论写回 review.md，状态改成对应的词。状态词统一为五个：`待审核 / 保留 / 重出 / 接受瑕疵 / 搁置`。`ShotRendersReader` 已经能解析「状态：」这一行。现有 19 条 review.md 用的是旧写法「已审核（…）」，统一解析为「已审核·未分类」。

### 10.5 归因（确定性规则，填进搁置单的「判断」一栏）

- 搁置原因与稳定的冷读发现在同一镜（±1）、同一类别族 → **设计为主**：先回上游提修改请求，不盲目重出。重出修不好设计问题；s2 如果把 st6、st7、st11、st12 都重出，每轮约 400 积分。
- 只有审核里的执行偏差、冷读没报 → **执行层**：重出，计数。
- 参考资产的问题（例如道具图画的是终态、宽高比超限）→ **补资产**：计数照算。
- 已列为能力上限的 → **换设计，或接受**。
- 都对不上 → **待人判**；同时自动生成一条「冷读漏报」的用例草稿，让逃逸回流成用例。
- 1b 之前还没有冷读报告，「判断」一栏按这几类由人填写。
- 不为一次随机失败加规则：同类问题在 ≥2 镜或 ≥2 场复现，或者你明确要求，才变成用例或改指南。

| 观众评分卡（T1） | 这些原则**做得好不好**，见 15.2 | LLM 独立上下文 + 你打分 | 不阻断；附在批准请求上作参考 |
| 回归用例 | 评分卡和确定性检查**会不会报**：用好坏成对的样本检验，见 15.3 | 免费（T0 部分）+ 订阅额度（T1 部分） | 改检查器或评分卡时作回归 |

「一切相连」不另立评分项：它的反面就是已有的缺陷类别 C5 状态因果、C6 道具因果、C7 只在文字里成立，按 §5.3 查。

### 15.2 观众评分卡

每项 1–5 分，**每个分数都要引用产物里的具体位置作证据**，不给总分，不设通过线；只看趋势，以及和你打分的一致程度。

| id | 维度 | 观众会问的问题 | 1 分 | 5 分 | 适用层 |
|---|---|---|---|---|---|
| S1 | Vision 契合 | 这一集或这一场，在给出全剧 Vision 要的体验吗？ | 和 Vision 无关，或者相反（例如写成 CG 过场感、爽文碾压） | 每段都能指出它服务 Vision 的哪一点 | 故事、分镜、成片 |
| S2 | 观众是主角 | 观众每一刻知道什么、在等什么？兑现得是时候吗？ | 按人物逻辑或事情先后平铺，期待没有建立，或者兑现太早、太晚 | 期待清楚；兑现前留了停顿；兑现、延迟、颠覆都有意图 | 故事、分镜、成片 |
| S3 | 体验优先 | 事件是为体验挑的，还是大纲凑出来的？ | 件件有事，却合不成一种体验 | 每个事件都对得上体验地图；开场一场先浓缩了本集体验 | 故事 |
| S4 | 戏剧顺序 | 观众被钩住了吗？交代是不是先行？ | 前段堆交代，最抓人的放在后面 | 开头就钩住；时间跳转观众跟得上 | 故事、成片 |
| S5 | 注意力 | 观众的眼睛落在设计的位置了吗？ | 构图、光、焦点各指一处，或者落点和设计不一致 | 每镜落点清楚，并与设计一致 | 成片（文字层不评） |

打分的方式：
- **独立上下文**：评分员只拿到 Vision、评分卡和被评的产物，不读作者的决策记录（否则就成了作者自评）。按 §8.2 的隔离要求，每份产物评 3 次，取中位数，并记下 3 次之间的离散度。
- **你的分数是准绳**：你在确定版本时用同一张卡打分（约 1 分钟）。先攒 10 份配对样本，算评分员与你的一致率（差距在 ±1 分以内的比例）。达到 70% 之前，评分员的分数只记录，不附在批准请求上。
- **落盘**：分数写进 `testlab` 的运行记录，管理 UI 按集、按场显示趋势。分数不回写创作产物，也不触发自动重写。

### 15.3 回归用例：用成对样本检验

绝对分数容易漂，**两个样本谁更好**要稳定得多。所以每个维度都准备「好 / 坏」成对样本，坏样本只改一个变量：

| 维度 | 好样本 | 坏样本（只改一处） |
|---|---|---|
| S2 | 兑现前留停顿（《群鸟》式） | 同一场，删掉停顿，人物一口气走完 |
| S3 | 事件都对得上体验地图 | 同样的事件数，换进 2 个和体验无关的孤儿事件 |
| S4 | 钩子场面放在开头 | 同样的内容，开头先放两段交代 |
| S1 | 抵达新地点时给建立镜头的奇观 | 同一场，写成 CG 过场式的平铺交代 |

- **用例怎么写**：沿用 §5.4 的格式。样本由一个不知道评分卡措辞的隔离会话改写，并遵守 §1.1 的防过拟合规则：评分卡与用例文本之间不得有连续 8 个字的重合。
- **门槛**：评分员必须在 3 次运行中稳定地把好样本排在前面（3/3）。每个维度至少 4 对，稳定排对的不少于 3 对，这个维度才算可用；否则这一维只保留你打分。
- **确定性检查**的用例是先红后绿：缺 Vision、有孤儿事件、场级缺「观众」小节，各一条，检查必须报出来。
